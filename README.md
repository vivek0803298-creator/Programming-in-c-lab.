# 🧪 Challenge Format

For each challenge, I try to understand:

### 1. Problem

What exactly is the problem asking?

### 2. Input

What data does the program receive?

### 3. Output

What should the program produce?

### 4. Logic

How can the problem be solved?

### 5. Implementation

How can the logic be converted into C code?

### 6. Testing

What happens with:

- Normal input?
- Minimum input?
- Maximum input?
- Invalid input?
- Edge cases?

### 7. Debugging

If the program doesn't work:

> **Why is it failing?**

Instead of simply changing code randomly, I try to understand the actual cause.

# 🔍 What I Am Learning From These Challenges

These challenges are helping me understand that programming is not about memorizing syntax.

For example:

```c
for (int i = 0; i < n; i++)
```

Learning the syntax is only the beginning.

The important questions are:

- Why do we need the loop?
- What is `i`?
- Where is `i` stored?
- How does the CPU execute this?
- What happens in memory?
- How many times does the loop execute?
- What is the time complexity?
- Can the solution be improved?

This repository is therefore focused on **understanding**, not just solving.

# 📊 Complexity Awareness

While solving problems, I will also gradually learn **time and space complexity**.

For example:

```text
O(1)       → Constant
O(log n)   → Logarithmic
O(n)       → Linear
O(n log n) → Linearithmic
O(n²)      → Quadratic
O(2ⁿ)      → Exponential
```

The objective is to eventually ask:

> **"Does this solution work?"**

and then progress toward:

> **"How efficiently does this solution work?"**

# 🐛 Debugging Philosophy

When my program fails, I will not immediately look for the answer.

I will first try to identify:

```text
What did I expect?
        ↓
What actually happened?
        ↓
Where did the behavior change?
        ↓
Why did it change?
        ↓
How can I fix the root cause?
```

This repository is also a record of my **debugging journey**.
